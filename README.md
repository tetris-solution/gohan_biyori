# マイ献立 — Cloudflare版

料理献立アプリをCloudflare Workers + D1で配信する構成。既存の食材保存方法ページも含みます。

## 実装済み

- ユーザー名・パスワードによるアカウント作成、ログイン、ログアウト
- PBKDF2-SHA256（100,000回）でパスワードをハッシュ化
- HttpOnly / Secure / SameSite Cookieによる30日間のセッション
- D1にユーザー別のレシピ・食材・献立・買い物・スーパー情報を保存
- 他端末からログイン／再読み込みした際の最新データ取得
- 更新バージョンによる同時編集の衝突検出
- 旧localStorageデータの明示的な取り込み
- 保存失敗時の通知、再送信、未保存データのダウンロード
- 同一IPからの認証試行を10分間20回に制限
- Same-origin検証、入力検証、CSP

現時点でメール確認・パスワード再発行・アカウント削除・リアルタイム同期は未実装。ユーザー名方式でメールを収集しません。パスワードは紛失すると復旧できません。写真のOCR・チラシ自動収集は未接続です。

## デプロイ

Cloudflareシークレットを環境に設定します。トークンや.envをGitにコミットしないでください。

- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`（対象アカウントのWorkers Scripts編集、D1編集、およびデプロイに必要なアカウント参照権限）

```sh
npm install
npm test
node scripts/provision.mjs
```

スクリプトは同名のDBを再利用し、なければ作成します。DB IDをwrangler.jsoncへ保存し、マイグレーション後にWorkerを公開します。workers.devのURLはデプロイ出力で確認します。初回のworkers.dev設定が必要なアカウントでは、Cloudflareダッシュボードで有効にしてください。

以降は `npm run db:migrate`、`npm run deploy`。ローカル開発は `npx wrangler d1 migrations apply gohan-biyori-db --local` と `npm run dev`。

## テスト

`npm test` はNode.jsの組み込みSQLiteで登録・認証・利用者間データ分離・更新衝突・ログアウト・認証試行制限を検証します。Node.js 24以上を推奨。Cloudflare実環境での最終検証は別途必要です。

## 公開環境

GitHub `tetris-solution/gohan_biyori` のmain更新をCloudflareのGit連携で配信します。公開URLは https://gohan-biyori.tetris-solution.workers.dev/ 。既存Sites版はこのDBに接続していません。実AI推論の確認には本番ログインが必要です。

## 画像保存（R2）

Cloudflare R2で非公開バケット `gohan-biyori-images` を作成します。公開URL・r2.dev公開・CORSは不要です。Workerの `IMAGES` バインディングに接続し、ログイン本人のみ取得できるAPI経由で配信します。料理・食材・レシートをJPEG/PNG/WebPで1枚5MBまで保存可能。R2保存・一覧・削除は実装済み、自動解析は未接続です。

現在のwrangler.jsoncにはユーザーが作成したD1のIDとR2バケット名を設定済みです。CloudflareのGit連携でのDeploy commandは `npx wrangler d1 migrations apply gohan-biyori-db --remote && npx wrangler deploy` としてください。先にR2バケットを作成し、CloudflareビルドのAPIトークンがD1のマイグレーションとR2バインディングに必要な権限を持つことを確認します。

## AI献立（Workers AI）

WranglerのAIバインディング `AI` を使い、`@cf/meta/llama-3.3-70b-instruct-fp8-fast` に食材・数量・気分・人数・調理時間・避けたい食材・計算済み栄養目標を渡します。朝昼晩の献立と分量・手順・1人分の推定栄養価をプレビューし、ユーザーが保存したときにレシピと献立をD1に保存します。不足食材は既存の買い物リスト追加を利用できます。写真はイメージ。写真のOCRは別機能で未接続です。

ログイン必須、1ユーザー1日10試行（日本時間、失敗も含む）。AI利用にはCloudflareの利用条件・モデルの条件・料金が適用されます。OpenAIのAPIキーは使いません。Workers AIを利用できるアカウントで、Cloudflareのビルド／デプロイ用トークンの権限も確認してください。

デプロイコマンドは同じです。`0002_ai_usage.sql` のマイグレーションも実行します。

```sh
npx wrangler d1 migrations apply gohan-biyori-db --remote && npx wrangler deploy
```

ローカルテストで認証・入力・回答形式・回数上限を検証済みです。Cloudflareの実AI推論・実DBへの保存はデプロイ後に検証が必要です。アレルギー対応はAI出力のみで保証せず、利用者が材料・調味料表示を確認してください。

## 栄養目標と食事記録

「栄養管理」の「目標を設定」またはアカウント設定から、年齢・計算区分・身長・体重・活動量を保存します。健康な18〜64歳の成人向けの維持カロリー概算です。Mifflin–St Jeor式にアプリの活動係数1.4／1.6／1.8を掛け、PFCをエネルギー比20:25:55で配分します。減量・増量、妊娠・授乳、治療食には対応しません。根拠のリンクは設定画面に表示します。

食物繊維・カルシウム・カリウム・食塩相当量は日本人の食事摂取基準2025年版を参考に年齢・区分で設定します。AI生成は材料から推定した1人分の栄養価を返し、サーバーでエネルギーとPFCの整合性を検証します。目標設定時にはカロリー±10%、各PFC量±15%、食物繊維・カルシウム・カリウムの下限、食塩の上限、カルシウム2,500mg以下を検証し、条件を満たさない回答をエラーにします。この判定は推定値に対するものです。食品成分データベースでの照合は未実装で、実際の摂取量の保証はできません。

1日の画面は予定量と食べた量を別々に表示します。食べたチェックは日付・朝昼晩別でD1に保存し、再タップで取消可能。チェック時の料理名・栄養値を記録するため、その後の献立変更で摂取記録は書き換わりません。複数人数のレシピでも集計は1人分です。栄養未登録の既存レシピをゼロ栄養とみなさず「未算定」と示します。プロフィールと食事記録はユーザー別JSONに保存し、追加のDBマイグレーションは不要。体格の生データはAIに送らず、サーバーで算出した栄養目標だけを送ります。

`npm test` で目標計算・入力範囲・栄養値の整合性・集計・AI目標制約・プロフィールと記録の保存を検証します。

## レシピノートへの取り込み

スマホのレシピ一覧は1列。登録方法はURL、写真・スクショ、手入力の3種類で、確認画面で修正してから保存します。URLは公開HTTPSページのJSON-LD Recipe・OGサムネイル・120文字以内の説明の引用と出典を取得し、AIで材料を構造化します。自動取得できないサイトは画像・手入力へ切り替えます。画像は本人専用R2からWorkers AI `@cf/meta/llama-4-scout-17b-16e-instruct` に送信し、読めない分量は推測せず空欄にします。URL解析は既存のLlama 3.3を使用。解析と献立提案は共通で1日10試行までです。

`requiredIngredients` に `{name, quantity, unit, amountText}` を保存し、既存の食材名配列は検索互換性のため維持します。g／kg／mg、ml／L、小さじ／大さじは換算し、袋とgなどの換算は行いません。合計必要量から在庫と未購入の買い物数量を差し引いた量を追加し、重複追加を防ぎます。購入済みを在庫へ移す際は同じ食材・換算できる単位の数量へ加算します。適量など不明な分量は要確認として扱い、勝手に数量を確定しません。食べたチェックでの在庫消費は行いません。プロフィールなどすべての登録フォームは今後も1列を維持します。

食材登録には保存場所（冷蔵庫・冷凍庫・常温）を持たせ、同じ名前でも保存場所別に登録できます。必要量の比較は保存場所をまたいで合計します。新しく購入した分は冷凍済みの在庫に混ぜず、冷蔵庫の在庫として登録し、必要に応じて編集で移します。

## 複数料理の献立と表示順

新しい献立は日付ごとに `{朝:[recipeId,...], 昼:[recipeId,...], 晩:[recipeId,...]}` で保存（各時間20品まで）。旧 `[朝ID,昼ID,晩ID]` は変換せずに読み取り互換性を保ち、編集時に新形式にします。食事記録も時間ごとの配列に対応し、旧単一スナップショットを保持して新しい記録を追加します。栄養集計は料理数に合わせて予定・完了を集計し、3品固定の判定を行いません。

一覧は登録日時の新しい順で表示し、古いデータは配列順・レシピIDから補完します。画像はR2の全ページのメタデータを取得して保存日時で並べ、100件単位の日時・IDカーソルでページ分割します。画像そのものは一覧のために読み込みません。大量の画像を扱う規模になった場合はこのメタデータ一覧を索引化する余地があります。

スマホではページ上部の紹介見出しを隠し、献立・レシピを写真＋情報の横並びカードにします。カード内のボタン・チェックは遷移を発火させません。レシピ詳細と保存方法詳細はハッシュURLで開き、ブラウザの戻る・再読み込みに対応します。

## 栄養管理とレシピの食材カテゴリ

「今日の献立」の右隣の栄養管理タブへ、1日の栄養バランスカードを移しました。献立と栄養管理の日付選択は共通で、食べた記録から集計します。`#nutrition` で直接開けます。レシピノートの食材カテゴリは、材料の登録済みカテゴリと食材名から判定し、選んだカテゴリを1つ以上使うレシピを表示します。キーワード・気分・時間・在庫条件と併用できます。
